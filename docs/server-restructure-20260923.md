## 5. 보존 대상과 초기화 범위
- 문제은행, 사건 자료, 모든 게임 규칙·버그 수정, 카드·팩·광휘 효과와 도감 규칙을 기준 커밋에서 보존한다.
- 교사 정책·학교/학급 범위, 게임/접근/노출/보상/출석/완성/미션 설정은 실제 DB에서 읽어 별도 RC에 보존한다.
- 저장소 기본값으로 현재 교사 설정을 덮어쓰지 않는다.
- 학생 테스트 기록은 새 RC에서 초기 상태로 시작할 수 있다. 이를 위해 기존 운영 DB를 먼저 삭제할 필요는 없다.
- DB가 연결되기 전에는 보존 설정 스냅샷이 생성됐다고 주장하지 않는다.

## 6. 개편 설계 초안 — 실제 DB 확인 후 확정

### 데이터 분리
- 학생, 교사·권한, 세션, 게임 시도, 완료 기록을 별도 테이블로 유지한다.
- 카드 일반/광휘 재고, 팩 재고·보장 조건, 개봉 결과, 광휘 조각·대표·잠금, 도감 완성 상태를 구분한다.
- 경험치·보상 지급 원장, 출석, 미션 실행 정의·학생 진행·수령 원장, 요청 영수증을 분리한다.
- 공통 설정은 버전을 두고 필요한 학교·학급·단원 범위만 읽는다.
- 학생별 행의 명확한 소유자 키와 조회 인덱스를 둔다. 기존 논리 테이블 명칭과 JSON의 의미는 보존하되 물리 테이블과 제약은 DB 확인 후 확정한다.
- 학생 전체 상태 JSON 한 덩어리로 재저장하거나 공통 namespace revision으로 모든 학생을 직렬화하지 않는다.
- 순위는 완료 기록을 바탕으로 필요한 범위만 인덱스 조회한다. 매 완료마다 전체 학생 순위를 재작성하지 않는다.

### 변경 처리와 무결성
- 요청 고유 키는 세션 토큰이 아니라 계정의 안정적인 식별자 + 요청 ID를 기준으로 한다.
- 작업 종류와 정규화한 payload의 해시를 저장한다. 같은 ID에 다른 요청이면 거부한다.
- 완료 기록에는 시도 ID 유일 제약, 최초/일일/미션/도감 보상에는 각각 의미에 맞는 유일 제약을 둔다.
- 동일 학생의 관련 잔액 행은 트랜잭션에서 잠그고, 다른 학생은 독립 처리한다.
- 팩 차감·난수 추첨·광휘/중복 판정·카드/조각 저장·도감/미션 반영·요청 영수증을 하나의 DB 트랜잭션 경계 안에서 확정한다.
- 실패 시 전부 롤백하며 응답 유실 후 재시도는 이미 확정한 결과를 반환한다.
- 교사 지급도 학생 요청과 같은 학생 재고 트랜잭션을 사용한다. 다수 학생 잠금이 필요한 경우 정렬된 키 순서로 획득한다.
- 게임 완료는 기존 답안·순서·인과·시간·연습모드 판정 규칙을 서버에서 검증한다. 클라이언트의 점수·완료·지급 수량을 그대로 믿지 않는다.
- 기존 도메인 규칙과 새 함수 사이의 일치 검사를 작성한다. 광휘 미획득 우선, 전부 수집 후 중복, 잠금, 대표, 완성 보상의 최초 1회 및 연쇄 방지까지 포함한다.

### 로그인·화면 연결
- 로그인: 인덱스로 학생 확인 + 세션 생성 + 최소 권한/프로필 응답.
- 메인 진입: 학습 해금·최소 보상 요약을 로드하고 카드/도감/미션은 필요 시 별도 조회한다.
- 출석은 멱등 처리하며 카드 전체 로딩을 로그인 완료 조건으로 두지 않는다.
- 게임은 기존 프런트 렌더링과 규칙을 활용한다. 클릭·문제 진행은 로컬에서 처리하고 서버 검증용 transcript를 누적한다.
- 기존 연결고리·순서형·짝맞추기 등 각 모드의 서버 의존 경로도 점검한다. 초급/중급만 바꾸고 전체 모드가 오프라인 즉시 진행된다고 주장하지 않는다.

### 완료 outbox
- IndexedDB에 안정적인 학생 키, 로컬 시도 ID, 시작 요청 ID, 완료 요청 ID, 문제은행/규칙 버전, 답안 기록을 저장한다.
- 시작 등록과 완료 전송의 의존 순서를 보존한다. prepare/activate 응답이 유실돼도 동일 게임을 다시 만들지 않는다.
- 완료 직후 결과 화면을 표시하고 '서버 저장 대기'와 '저장 완료'를 구분한다.
- 서버 확정 전에는 팩·카드·경험치 지급을 확정 표시하지 않는다.
- 새로고침·연결 복구·같은 학생 재로그인 시 재전송한다. 다른 학생 로그인 중에는 이전 학생 자료를 현재 학생 토큰으로 전송하지 않는다.
- 다중 탭 전송도 서버 멱등성으로 방어한다.
- 영구 검증 실패와 일시 네트워크 실패를 구분하며 실패 자료를 조용히 삭제하지 않는다.
- 로컬 저장 자체가 실패할 때에도 저장됐다고 표시하지 않는다.

### 일괄 등록·권한
- 기존 명부 한 번 전송 UI를 유지하고 DB에서 명부 전체 검증 및 set 기반 insert/upsert 정책을 적용한다.
- 중복 학생 정책·학교/학급 권한·코드 발급 영수증을 한 번 검증하고 처리한다.
- RLS 적용, 불필요한 anonymous/authenticated 직접 쓰기 차단, 함수 실행 권한 최소화.
- 학생이 교사/관리자 API·RPC를 직접 호출하는 부정 시험 포함.
- service role이 RLS를 우회할 수 있으므로 Edge/RPC 내부 역할·범위 검증을 별도로 유지한다.
- 로그인 제한은 학생 전체를 막는 공통 카운터 쓰기를 피하면서 계정별 공격 방어를 유지한다.
- 로그는 요청 ID·작업·시간·결과 코드 중심으로 제한한다. 코드·토큰·전체 답안·학생 개인정보를 로그에 출력하지 않는다.

## 7. 별도 RC와 커밋 순서
1. Supabase 연결 후 실제 스키마·함수·RLS·인덱스·설정·데이터 규모를 읽기 전용으로 확인.
2. 보존할 설정 스냅샷과 복구 경로 확보. 코드 설계와 실제 DB 차이 반영.

4. 서버/DB/데이터 처리 및 완료 outbox 구현 커밋.
5. 최소 무결성 시험과 실제 RC 브라우저 흐름 시험. 성공 체크포인트 생성.
6. UI 변경은 별도 커밋:
   - 고급 코드·문항 보존, '기출 문제형 · 준비 중' 비활성화.

## 8. 검증 계획과 합격 판정
- 실제 RC 배포 주소의 학생 화면을 브라우저로 조작한다.
- 학생 선택 → 로그인 → 출석·최초 상태 → 게임 시작 → 실제 정답/오답 진행 → 완료 저장 → 보상 확인 → 팩 개봉 → 로그아웃 → 재접속 → 기록·재고 유지.
- 5명 → 15명 → 30명, 각 단계에서 실패 시 원인 확인 후 다음 규모 진행.
- 25명 로그인 목표도 별도로 측정한다. 30명 결과로 25명 실측을 대체하지 않는다.
- 차가운 시작/따뜻한 시작, 기존 운영 규모에 상응하는 데이터량, 서버 처리시간/클라이언트 체감시간을 구분한다.
- 보존한 설정, 데이터 행 수·바이트, 소스/배포 커밋, 대상 URL, 실행 시간대를 시험 증거에 기록한다.
- 메모리 fakeStore, API만 직접 부른 부하 시험, 다른 Edge Function 결과는 이 합격 판정에 사용하지 않는다.
- 응답 유실 후 재시도, 동시 동일 요청, 같은 ID 다른 payload, 다른 ID 동일 완료, 한 팩 동시 개봉, 재로그인 후 outbox 재전송, 교사 직접 호출 차단을 검사한다.
- 실제 재고와 원장을 DB에서 대조한다. UI가 성공했다고 표시하는 것만으로 누락 0건으로 판정하지 않는다.
- 최소 성능 목표: 25명 로그인 대부분 10초 이내; 게임 화면 전환 2초 이내; 문제 진행 즉시; 마지막 문제 후 완료 화면 즉시; 완료 서버 반영 대부분 10초 이내; 팩 개봉 대부분 5초 이내.
- '대부분'은 시험 보고에 목표 이하 인원/전체 인원과 p50/p95/최대값을 함께 남긴다. 잠정 자동 판정 기준은 p95를 사용한다.
- 정확성 목표: 기록·카드·팩·보상 누락 및 중복 완료·보상·카드 지급 각각 0건.
